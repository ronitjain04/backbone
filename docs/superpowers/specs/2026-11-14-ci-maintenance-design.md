# CI/CD hardening and targeted technical-debt removal

Date: 2026-11-14. Status: approved by the user; implementation authorized.

## Purpose and current state

Make Backbone's company demo easier to maintain and safer to release, with stronger automated evidence that chat, saved practice and the teacher workspace still work. Keep Vercel, FastAPI, PostgreSQL/Neon, plain JavaScript and the existing Groq integration.

The current public main has guided practice (PR 11); PR 12 contains the interactive classroom work and is still open. Implement this as a separate stacked PR against PR 12's branch, so the cleanup diff can be reviewed independently without merging either PR. Merge order is classroom first, maintenance second; retarget maintenance to main after the parent lands. No merge or production promotion is authorized by design approval alone.

## Approaches

Recommended builder choice: strengthen the existing pipeline and remove specific duplication while retaining verified live consumers. Add reliable quality, migration, browser and dependency checks; verify a release candidate before assigning the public domain; consolidate local development on the production FastAPI gateway.

A checks-only change would be smaller but leave duplicated runtime behavior and unsafe deployment ordering. A broad rewrite of the backend/frontend or replacement of the hosting stack would increase demo risk and is unnecessary. The focused approach is the builder's recommendation, not a user-selected architecture change.

## Audit findings and priority

1. **Release ordering:** `.github/workflows/ci-deploy.yml` runs `vercel deploy --prod --yes` before revision/readiness/live-answer verification. A failed smoke test reports failure after the public site already changed. Stage a production-configured deployment with `--skip-domain`, verify that exact candidate, recheck main's revision, then promote it. A failed candidate must never be promoted.
2. **Duplicate and wasteful workflow runs:** push and pull_request both run for the same feature commit; stale verification runs are not canceled. The daily schedule currently runs the deployment job on main and can redeploy unchanged code. Use PR checks plus main pushes; cancel superseded verification runs, serialize promotion separately, and put daily health/model monitoring in a workflow that cannot deploy.
3. **Missing browser-level release evidence:** current JavaScript tests use JSDOM and static/Worker builds, while CI has no real browser check of the combined FastAPI app. Add headless Chromium coverage against a local full-stack server, an isolated PostgreSQL database and deterministic fixture retrieval/model responses. Cover student draft refresh, help/correction/follow-up outcomes, teacher inspection, replay and mobile overflow. Preserve the separate optional live-provider probe so provider quotas are not misreported as deterministic product regressions.
4. **No explicit migration-upgrade gate:** CI executes store migrations in isolated tests, but has no named upgrade compatibility check on populated old schema. Add a required old-schema-to-current migration check with row preservation, rerun idempotency and historical outcomes, using synthetic data. Never copy private production student data into CI.
5. **Dependency and workflow checks:** pytest is installed without a version constraint; runtime dependencies are duplicated between `website/pyproject.toml` and `backend/requirements.txt`; Docker uses Python 3.11 while the deployment requires 3.12. Pin development tools, enforce runtime declaration equality with a contract test, align supported Python runtime declarations, validate workflow syntax, and scan actual production dependencies for known high/critical issues. Resolve tools/patch versions from official sources during implementation and pin actions by full SHA. Add grouped weekly Dependabot updates for GitHub Actions, production Python and npm dependencies; bot updates are PRs, never automatic merges.
6. **Duplicated local runtime and unclear hosting ownership:** `website/site/proxy.mjs`, `dev.mjs` and `build.mjs` implement a second chat gateway and Worker deployment path. Vercel uses static assets and `backend/site.py`, while a read-only Sites connector check confirmed the older Sites publication is still active at version 6. Preserve its Worker gateway, build and compatibility tests. Standardize default local development on the combined FastAPI gateway so practice and teacher flows work locally. Keep `npm run build` as the canonical Vercel static-build command, retain `build:static` as an alias, and expose the existing Worker build explicitly as `build:sites`. Remove the extra standalone Worker build step from the Vercel workflow where equivalent compatibility coverage already builds it in tests. Replace the chat-only Node preview launcher with a combined-gateway launcher that builds assets and emits a clear dependency/env setup error. Rewrite the guide to distinguish active Vercel deployment, current local development and the retained Sites compatibility path. Do not delete a live consumer merely to shrink the repository.
7. **Classroom query round trips:** `website/backend/practice/classroom.py::classroom` performs definition/progress/latest-check/hint-count/expiry lookups inside the per-student loop. Five-second polling therefore scales database network round trips with classroom size. Batch read projections, retain on-demand evidence, and handle expired reservations under deterministic session-lock ordering. Tests must show the normal no-expiry read query count stays bounded for one versus 30 students, without changing response shapes or diagnostic/ownership behavior.
8. **Smaller current debt:** Store error types are imported back into `classroom.py` from its subclass module, creating runtime circular coupling; move shared errors to a small module while preserving import compatibility where tests/consumers need it. Remove duplicate owner/classroom replay controls from the student page now that `/teacher.html` owns this flow. Fix the deferred legacy replay completion badge conservatively; do not label historical work independent. Remove genuinely unused imports and unreachable helpers identified by the configured lint checks.

Historical `backbone-ui` and `backbone-i2p` folders have separate original applications, raw HTML rendering and their own dependencies. They are not the live Vercel entrypoint. Preserve their attribution and original sources; document them as legacy rather than bulk-deleting or claiming to have security-certified them. A later archival/migration decision is separate work. No demonstrated security vulnerability is asserted merely because a legacy file uses innerHTML.

## Pipeline and deployment behavior

Required PR/main gates: workflow validation and basic Python/JavaScript lint; locked/pinned tool installation and dependency-declaration check; backend/deployment unit and real PostgreSQL integration tests; explicit populated-schema migration upgrade; frontend unit tests and static build; Chromium full-stack smoke with failure artifacts; dependency vulnerability checks. Use narrowly scoped workflow permissions, pinned third-party actions, finite job timeouts and cached package installs. Pull requests, including forks, must not receive deployment/model/database secrets; their fixture database is disposable.

Keep browser fixtures out of production routes: run a test-only server entrypoint under the tests/support tree with known synthetic corpus, model and teacher credential. Production bundles/functions exclude it. Browser failure artifacts may contain only synthetic test data, with short retention. Do not use screenshots or traces from private course/user sessions as public CI artifacts.

Main release: reuse the tested static artifact, deploy the exact tested commit as an unpromoted candidate, verify health/revision/course configuration and a disposable practice save/check/replay/ownership cycle, then promote only if all required candidate checks pass and remote main still matches. The practice smoke deletes only its own newly created synthetic student session. Use the existing Vercel CLI authentication for protected candidate requests; do not disable deployment protection, add secrets to URLs, or expose credentials in logs. Record candidate URL/commit and promotion result in a job summary.

Candidate deterministic checks gate promotion. A small real-provider answer probe remains a separately reported manual/scheduled check, with bounded retries respecting Retry-After and a clear distinction between provider quota/network failure and product regression. The scheduled monitor never redeploys unchanged main. After promotion, verify the public alias serves the expected revision; report a failed final alias check with the known previous deployment and recovery instructions. Do not automatically apply destructive database rollback. Candidate staging is not a database rollback boundary: additive migrations must remain backward-compatible with the previous app, and the report must state this limitation.

Dependency scans apply to the active production package sets, not the historical app trees. Patch-only remediation is in scope when compatible and covered by tests. For a finding requiring a major upgrade or a disputed exception, document the exact advisory and impact and bring that concrete decision back to the user; do not blanket-ignore findings or fail the pipeline on irrelevant dev-only packages without inspection.

## Code/debt boundaries

Separate operational scripts from product code. Deployment transport and candidate/promotion orchestration must be testable without contacting Vercel. Keep existing same-origin authorization, source verification, idempotency, assistance attribution, token privacy and response contracts. No UI redesign, model-provider migration or new paid service. Avoid reformatting historical projects or expanding cleanup into unrelated feature work.

Preserve existing Sites compatibility coverage and meaningful coverage from replaced local-runtime tests on the production gateway. A smaller raw test count after removing duplicate proxy tests is acceptable only when equivalent active-path behavior remains covered and the report maps migrated coverage. Runtime error handling must remain user-facing and non-secret-bearing.

- Verify browser student/teacher/replay flows at desktop and phone dimensions, with saved work after refresh and no page-wide horizontal overflow.
- Publish a maintenance report listing removed duplication, retained legacy debt, before/after classroom query counts and relevant timings, CI/CD protections and limitations.
- Create a separate review PR, wait for its CI, and retain PR 12 unchanged. Production remains on the current public release until the user authorizes merge/promotion.

The builder chooses component names, exact stable pinned tool versions, query batching strategy, browser fixture organization, artifact retention within seven days, and test decomposition. The builder must verify the available Vercel CLI candidate/promotion commands before wiring them into CI. If a legacy deployment is discovered to still depend on the Worker path, preserve that consumer and document the constraint instead of silently breaking it; the supported public Vercel path remains the target.
